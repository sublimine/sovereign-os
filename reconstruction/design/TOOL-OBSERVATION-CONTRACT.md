# Tool observation and inference exposure contract

Implemented in the new factory registry, not the withdrawn prototype. The trusted dispatcher calls `recordToolObservation(runId, signedReceipt)` before building and dispatching the next inference. A tool observation is not a model-authored receipt.

The registry verifies the authority signature and the exact committed broker effect (ID, actor, mission, tool, argument hash, terminal status and signed receipt hash). Same-mission external observations retain their original actor and `EXTERNAL_OBSERVATION` relation. They cannot be declared as the observer's own action. Cross-mission, altered and uncommitted receipts fail closed.

`getToolObservations(runId)` returns a detached array with `id`, `hash`, `principalId`, `relation`, `tool`, `status`, `result`, `quoteText`, and `observedAt`. The hash is SHA-256 of the canonical signed receipt, including its signature. `quoteText` is `canonical(receipt.result)` (sorted object keys), not an unsorted JSON serialization. Review evidence uses `{kind:'tool',id,hash,quote}`, where quote must be an exact nonempty substring of that canonical result. The dispatcher must actually include these observations in its inference input; this trusted manifest API is not a substitute for dispatching the bytes.

Context source/artifact exposure is monotonic. Observations cannot be added while an inference request is pending. New context or tool observations invalidate the completed-exposure marker until a new inference completes. The provider receipt must match the recorded request hash; every scoped inference uses a fresh thread. Independent review checks every producer and reviewer inference thread, not only the most recent pair. Producer artifact tool receipts must be successful, durable, producer-owned and observed before the final producer inference.

ACCEPT requires successful cited tool operations. Failed operations remain usable for RETURN/UNKNOWN diagnosis; a failure does not establish that tests passed. A workspace read used as current-state acceptance proof must belong to the reviewer and have been dispatched after candidate creation. This order uses committed journal sequence, not potentially equal clock timestamps. If the candidate declares a write to that path, the current read hash must equal the declared write's hash. The read bytes must match their own hash. This establishes an observed version, not semantic correctness or complete test coverage.

External mutation does **not** automatically invalidate historical receipts or accepted artifacts. `assertUsable` verifies historical acceptance and provenance, not current filesystem or network state. Final consumers requiring current material state must arrange another read/verification at consumption and reject changes. A mere string `PASS` is not a runner attestation. At this document's initial implementation cut the broker lacked an execution runner; the subsequent isolated runner and its actual launch-proof contract are documented in [EXECUTION.md](../../factory/tools/EXECUTION.md). Those later capabilities do not retroactively turn historical text or simulated receipts into execution evidence.

Source-fetch receipt citations have a second, epistemic admission check: an authentic successful acquisition is not enough for ACCEPT. The exact associated source must still be ADMITTED and match receipt and content hashes. Retraction invalidates acceptance that cited the source through either source-kind or tool-kind evidence, including downstream products. `assertUsable` rechecks this relationship. RETURN/UNKNOWN can retain historical withdrawn receipt evidence for diagnosis. Uncited acquisition receipts are not automatically factual claims.

The WorkerService now also performs a synchronous real-workspace snapshot comparison immediately before registry acceptance; later consumers must repeat that point-of-use check. This is a control-plane validation, not a new model observation or an OS lock against external mutation.

## Runtime-evaluated acceptance criteria

Criteria may declare `evaluation` as `content` (the default), `runtime.independent_review`, `runtime.no_file_writes`, or `runtime.no_code_execution`. The caller submits checks for exactly the content criteria, including an empty check array when all criteria are runtime-evaluated. Runtime check IDs and `kind:'control'` evidence cannot be supplied by the caller.

After checking actual reviewer identity, disjoint producer threads, completed inference and observed candidate, the registry generates runtime checks in the same transaction as the review. Each has a signed `review.control` record stored under `review-control`, bound to artifact/hash, reviewer, criterion/evaluator, exposure and inference receipt hashes, evaluated effect record versions, verdict and checkpoint time. There is no requirement for the review record to preexist itself.

Absence controls inspect all matching broker effect intents in the mission, not the model's selected observations. No matching intent yields PASS; a terminal matching attempt yields FAIL conservatively, including failed unavailable execution; pending or uncertain intent yields UNKNOWN. These controls concern broker-mediated mission operations, not host-wide filesystem/process surveillance or incidental control-plane persistence. FAIL/UNKNOWN turns proposed ACCEPT into a recorded RETURN with a material finding. Historical records remain inspectable. `assertUsable` verifies control signatures and bindings and rejects an absence certificate if a later matching mission effect exists.

Six dedicated `control-criteria.test.mjs` cases cover atomic non-self-referential independent review, rejected caller fabrication, real unobserved file writes, unavailable execution attempts, subsequent writes and pending durable intent. The pending-intent case is explicitly a unit fixture, not a claimed file effect.

Validation: 23 tests in `tests/factory/adversarial-core.test.mjs` pass, including the original AC01–AC11 regressions, multiple-inference isolation, forged/uncommitted observations, foreign ownership, delivery-before-inference, real filesystem reobservation, stale read sequencing with equal timestamps, changed file bytes, and diagnostic failed reads. Inference receipts are synthetic fixtures; HTTP is injected fixture transport. These results do not claim live model quality, full system completion, or hostile host-administrator isolation.
